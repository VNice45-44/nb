to:

2) Suggested API contract for UI

The UI needs “a list of active dates”. So backend can return either:

    a list of dates: [ '2026-08-01', '2026-08-02', ... ]
    or rows from which the UI derives dates.

Given the SQL shape, easiest is: query distinct activity_date for the notebook.
3) Active day definition

A day is active if there is at least one row where:

    machine_id = selectedMachineId
    activity_kind = 'edit' (for the first pass)
    and activity_date falls within the displayed window (e.g. last 28 days)

4) Write behavior to implement next (edits -> upsert)

On any meaningful notebook edit, insert/upsert today as:

    activity_kind = 'edit'
    activity_date = current_date
    machine_id + owner_id set from the edit context (owner is the signed-in user)

Your backend write should do an upsert respecting the unique constraint:

    (machine_id, activity_date, activity_kind)

5) Migration order update

    Read calendar from machine_activity_days (keep layout logic the same)
    Later, implement write-updates from notebook edits

6) RLS implication for frontend

Because RLS enforces owner_id = auth.uid(), the frontend should only see activities for notebooks that belong to the signed-in user (consistent with your existing ownership model). No special handling beyond filtering by machine_id.
